# ТЗ: надёжность бота, панели и ловца чеков (24.09.2026)

Цель — чтобы ни бот, ни «🛰 Панель», ни ловец чеков не падали и не зависали от
сбоев сети, SQLite или Telegram, а временные данные и карточки убирались сами.

Найдено чтением кода:

* Ловец чеков: разговор с ботом кошелька (`_await_replies`, `get_messages`) не
  ограничен по времени и идёт под замком (аккаунт, бот) — зависший запрос держит
  замок, и все следующие чеки этого аккаунта ждут. Нажатие `startBot` при
  FloodWait молча спит внутри Telethon до 60 с (чек уходит), а при любой ошибке
  нажатия чек никто больше не берёт: отметка «взят» стоит на коде.
* Карточка-реле (капча/пароль) через 30 мин забывается в памяти, но в чате
  остаётся с мёртвыми кнопками.
* Панель: uvicorn при занятом порту делает `sys.exit(1)` — `SystemExit`
  не ловится супервизором (`except Exception`) и роняет **весь процесс**.
  Необработанная ошибка эндпоинта отдаёт голый `500 Internal Server Error`,
  `fetch` на странице не имеет таймаута — подвисший туннель оставляет скелетон
  навсегда; необработанный промис в действии экрана молча глотается.
* `host_stderr.log` дублирует весь `app.log` (консольный хэндлер на INFO).

## Этапы

### 1. SQLite и event loop
1.1 **Удаления пачкой.** `delete_handler` → одна функция на событие:
    сначала read-only `SELECT … WHERE message_id IN (…)`, запись только если
    строки нашлись, одна транзакция на всю пачку. Одно и то же удаление,
    пришедшее восьми аккаунтам, обрабатывается один раз (`remember_message`).
1.2 **Хэндлеры аккаунтов не бросают.** `NewMessage` / `MessageEdited` /
    `MessageDeleted` обёрнуты: ошибка — одна строка лога (трейс не чаще раза
    в минуту на хэндлер), не `Unhandled exception` от Telethon.
1.3 **Прогресс скана — не повод обрывать скан.** `mark_processed_units` и
    прочие записи прогресса best-effort.
1.4 **busy_timeout 5 → 10 с** и повтор при `database is locked` (до 3 раз с
    джиттером) для фоновых писателей: `update_scan_run`, `save_checkpoints`,
    `recalculate_source_scores`, удаления.
1.5 **`/api/health` не ждёт базу дольше 2 с**: SQL-поля — через `wait_for`,
    по таймауту `null` + `db_slow: true`. Статус от этого не деградирует —
    watchdog перезапускает только мёртвый процесс.
1.6 **Детектор залипания event loop.** Поток-сторож: loop отмечается каждые
    0,5 с; если отметки нет > 3 с — WARNING со стеком главного потока (что
    именно держит loop), один раз на залипание. `loop_lag_ms`, `loop_stalls`,
    `loop_max_stall_ms` — в `/api/health`.

### 2. Ловец чеков
2.1 **Таймауты.** Каждый `get_messages` при опросе — ≤ 10 с; весь разговор
    после нажатия — ≤ 45 с (`asyncio.wait_for`); `get_chat` для карточки ≤ 5 с;
    действия реле (кнопка/ответ/повтор) ≤ 40 с. Замок (аккаунт, бот)
    освобождается всегда.
2.2 **Фейловер нажатия.** `startBot` с `flood_sleep_threshold=0`. Если само
    нажатие не ушло (FloodWait, обрыв, ошибка RPC) — общий чек передаётся
    следующему онлайн-аккаунту, который включён и не на кулдауне (до 2
    передач). Аккаунт с FloodWait получает кулдаун на срок ожидания и
    пропускается при выборе. Личный чек не передаётся (взять может только
    адресат). Правило «один чек — один аккаунт» сохраняется: передача только
    когда нажатия не было.
2.3 **Протухший peer.** Ошибка резолва/нажатия сбрасывает кэш `_bot_peers` для
    (аккаунт, бот).
2.4 **Меньше шума.** Заведомые не-чеки (`inv_`, `i_` у xRocket; `IV`, `r-` у
    CryptoBot; `U…` у RedCube; `ref…`/цифры у Rampage) не пишутся как
    «не распознан».
2.5 **Карточка-реле убирается.** id карточки хранится в реле; по истечении
    30 мин janitor правит её в «⌛ Истекло» без кнопок.
2.6 **Счётчики** (нажато, забрано, ошибок, передач, последняя ошибка) — в
    `/api/health` → блок `checks`.

### 3. Панель
3.1 `serve_miniapp` превращает `SystemExit` uvicorn в обычную ошибку —
    супервизор перезапускает сервер с backoff, процесс живёт.
3.2 Глобальный обработчик ошибок: `database is locked` → `503` +
    `Retry-After: 2` и «База занята — повторите»; остальное → JSON `500`
    «Внутренняя ошибка — записано в журнал», ERROR в лог и `app_events`
    (не чаще раза в минуту на путь).
3.3 Клиент: таймаут `fetch` (чтение 20 с, действие 45 с, вход в аккаунт 90 с);
    таймаут и `502/503/504` для чтения → снимок офлайн, как при обрыве; одно
    автоповторение чтения на `503`; для действия — честное «ответа нет,
    действие могло пройти — обновите экран».
3.4 `unhandledrejection` / `error` → тост, а не мёртвый экран.
3.5 Лимитер забывает пустые ключи.

### 4. Логи и автоочистка
4.1 Схлопывание шума Telethon: повторяющиеся `Security error…`,
    `Server closed the connection…`, `Attempt N at connecting failed…` — первая
    строка в минуту на шаблон, потом «(повторилось N раз)».
4.2 Консоль (`host_stderr.log`) — только WARNING+, когда stderr не терминал;
    трейсы падения до настройки логов всё так же попадают туда.
4.3 `FILE_RULES`: ротированные `runtime.out.log.*`, старые `restart_*.log` в
    корне и `app.log` в корне (пишется в `logs/` с мая) — удаляются по возрасту.

## Не входит
* Переезд с aiosqlite/одного файла SQLite на что-то другое — после 1.1 и 1.6
  нужны данные сторожа, прежде чем менять хранилище.
* Лечение сетевых обрывов (`WinError 121`) — внешняя причина; задача — чтобы
  после них всё поднималось само, это покрыто.

## Приёмка
* `pytest` зелёный, на каждый пункт — тест.
* После рестарта живого приложения: `/api/health` отвечает с новыми полями,
  в логе нет `Unhandled exception on delete_handler`, панель открывается.

  каждую победу с каждой, 2,9 с на event loop при каждом старте. Теперь строки
  группируются по нормализованному тексту (результат тот же — закреплено тестом
  против старого алгоритма) и считаются в потоке.
* Сверх ТЗ: супервизор джобов перезапускает и после `SystemExit`; service worker
  панели ждёт сеть 6 с и отдаёт кэш вместо 5xx-страницы туннеля; кэши
  `/api/app/pulse` и истории курсов выбрасывают устаревшие записи; карточка
  реле после текстового ответа запоминает новый id (закрывается именно она).
* Передача нажатия (2.2) делается и при обрыве соединения, не только при
  FloodWait — пропущенный чек дороже лишнего нажатия; при таймауте — нет.
